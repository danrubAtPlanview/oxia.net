# Benchmark results

Generated by `benchmarks/make-results-doc.py` from a BenchmarkDotNet `--job short --memory` run of the whole suite (108 benchmarks in 15 classes).

Environment: BenchmarkDotNet v0.15.8, Windows 11 (10.0.26100.9711/24H2/2024Update/HudsonValley), Intel Core Ultra 9 185H, .NET 10.0.14 (10.0.14, 10.0.1426.52326)  
Logical cores: 22, build configuration: RELEASE

**Read these as ratios, not absolute truths.** The short job takes 3 iterations on a shared Windows workstation (Docker Desktop and an IDE were running); expect 10-20 % run-to-run noise. Allocation numbers (B/op) are exact and are the figures that matter for the zero-allocation goal. The long-job, head-to-head-with-Go numbers of the end-to-end client are in [`performance.md`](performance.md); the allocation protocol and the before/after of the response pooling are in [`performance-allocation.md`](performance-allocation.md).

## End to end against a real Oxia server: .NET vs the Go client

Same machine, same container (`oxia/oxia:nightly-beta` = the pinned upstream commit, one fresh `oxia standalone` per run, 1 shard, notifications on),
same workload: 100 000 keys, 128 B values, closed loop, 12 s after a 3 s warm-up, one run each (`load` mode of the benchmarks exe;
the Go client is built from the pinned checkout by `Load/go/build.ps1`). Docker Desktop on Windows adds loopback latency to both sides equally.

| Scenario | Client | ops/s | p50 ms | p99 ms | p99.9 ms | client CPU us/op | allocated B/op | GCs (gen0/1/2) |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| A: async, 256 producers, put+get 50/50, linger 5 ms | **.NET** | **36,537** | 7.27 | 10.36 | 13.30 | 12.04 | **119** | 4 / 1 / 1 |
| | Go | 35,760 | 7.31 | 9.77 | 11.67 | 10.16 | 1,662 | 18 / - / - |
| B: async, 1000 producers, put only, linger 5 ms | **.NET** | **88,478** | 10.55 | 22.81 | 30.80 | **4.41** | **6** | **0** / 0 / 0 |
| | Go | 71,296 | 13.24 | 27.26 | 34.08 | 11.03 | 1,972 | 10 / - / - |
| C: sync client, 64 callers, put+get 50/50 | **.NET** | **10,767** | 6.26 | 7.44 | 8.91 | 18.38 | 791 | n/a |
| | Go | 10,213 | 6.29 | 7.31 | 8.45 | 13.51 | 1,812 | n/a |

Reading it: throughput and latency are at parity with Go when the server is the bottleneck (A, C) and clearly ahead when the client is
(B: +24 % ops/s with 2.5x less CPU per operation and ~0 allocation: 6 B/op against Go's ~2 KB/op, no GC at all in 12 s of 1 M puts). The
.NET client uses more CPU per operation at low concurrency (scenario C: 1.36x; thread-pool spin-waiting plus one gRPC `Read` call per get batch, see
[`performance.md`](performance.md)). Allocation in A and C is dominated by the value arrays the faithful `Get` API must hand to the caller (the
pooled read API in `Oxia.Client.Pooled` removes them).

## End-to-end allocation profile (`alloc` mode)

Client and an in-process zero-allocation echo-style server in one process, 400 000 operations per scenario, per-type attribution from sampled GC
allocation ticks (full output with the per-type breakdown: run `... -- alloc`). The `Io.Oxia.Proto.V1.*` rows in the raw output are the *server*
side (protoc-generated types); the client-only budgets asserted by the test-suite are in [`performance-allocation.md`](performance-allocation.md)
(Put 4.5 B, Delete 10 B, Get-not-found 5 B, faithful found-Get 133 B of which 124 B is the required `byte[]`, pooled Get 5 B, pooled scan 2.3 B/record).
